title: Pick a project

The best next project is one you'd enjoy changing after the basic version works. These guides give you a destination and a path, but they don't provide finished code. You'll decide how the program looks, how its data is organized, and which extra features are worth keeping.

## Three starting points

| Project | What you will make | Good practice for |
| --- | --- | --- |
| [Typing trainer](./typing-trainer/) | A page that shows a phrase and measures how fast and accurately you type it | Keyboard events, strings, timers |
| [Sticker board](./sticker-board/) | A board where you place, drag, and delete emoji stickers | Mouse events, coordinates, classes |
| [Flashcard deck](./flashcards/) | A study deck you flip and sort with keyboard shortcuts | Classes, modules, keyboard shortcuts |

You can move any project into a setting you care about. A typing trainer can drill your org's terms. A sticker board can become a seating chart. Flashcards can cover a subject you're studying this term. Keep the first version small before changing the theme.

## Work in versions

Every guide has milestones. Finish one, check it in the browser several times, then save a Git commit before beginning the next. A milestone is useful only when the program works at that point. Half of three features is harder to debug than one finished feature.

Start each project in its own folder with three files: `index.html`, `style.css`, and `main.js` loaded with `type="module"`. Open the folder with Live Preview. Don't copy Bop the Bot and delete parts until it resembles something new; starting fresh makes you decide what this program actually needs.

Your first version may have fixed data written in the file. That's fine. Add user input after the display works. Add keyboard shortcuts after the mouse version works. Add saving after the program behaves correctly while the page is open.

## Keep a small project note

Before coding, write four short answers in a README or on paper:

1. Who will use this program?
2. What should they be able to do in the first finished version?
3. What information must the program remember while it runs?
4. What result tells you the program worked?

These answers are your first specification. Change them when you learn something, but write down the change. Otherwise the project can quietly grow until nothing feels finished.

## When to ask for help

Ask about one behavior at a time. Show the current result, the result you expected, and the smallest part of the program that reproduces the problem, along with any red text from the console. Someone can guide you without taking over the project.

There is no required final design. If your version completes the core checks on its project page and you can explain its main decisions, it's finished enough to share.
